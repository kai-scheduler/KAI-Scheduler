Semi-preemptible: open design issues
KAI-Scheduler · PR #1804 (merged 2026-09-23) · 2026-10-06 · brainstorm input
Alpha · Brainstorm
Why / Context

Semi-preemptible protects a job's minimal satisfying shape (minMember per leaf, minSubGroup per set) and lets everything above it run elastically over-quota. Intent: important enough to always run, not important enough to hog.

The first implementation works for the happy path. The two reported issues, and most of what else we found, share one cause:

Core is derived, not admitted. Quota is gated once, when a pod is allocated. Which pods count as core is then recomputed every session from live state. Nothing re-checks the quota gate when that recomputation changes the protected charge.
How it behaves today
  • 🔀Leaf core = the minMember oldest allocated pods (task order falls back to creation time, then UID).
  • 🔀Set core = the minSubGroup members ranked satisfied-first, then by name (core_info.go).
  • ⚡Charge: once the min is satisfied, new pods charge 0 against non-preemptible quota (coreRequiredQuota). Queue AllocatedNotPreemptible then follows the recomputed core with no gate (semiPreemptibleCoreDelta).
  • 🔑Guards: webhook rejects minMember/minSubGroup increases; the resize validator quota-checks core pods only.
  • 🗑️Eviction offers only surplus, youngest first, role-agnostic within a leaf.
Reported issues

1Heterogeneous subgroups are not distinguished on reclaim

Mechanism

  • minSubGroup: 1 over {decode, prefill} means "any 1 of 2". Core goes to the first satisfied member by name, so decode always wins. Renaming a subgroup changes which one is protected.
  • The other role is reclaimed as a whole. A surviving prefill with no decode serves nothing.
  • If the roles cost different amounts (1 GPU vs 8), the protected charge flips when satisfaction order changes. The code already notes this as an alpha limitation (coreRequiredQuota).
  • SubGroup has only name, min*, parent and topology. The user has no way to say "this one is core".

Options

  • A. Subgroup coloring (isCore, team proposal). Optional field on SubGroup. It lets the user say which sibling holds the protected slot. Unset means today's behavior. See the HLD below.
  • B. Contract + nesting, no API change. Model roles as separate SubGroupSets under a root with minSubGroup = #roles. Works today. Ships as docs, and stays the guidance for interchangeable siblings, but it does not let a user pick one of several siblings.
  • C. Integer rank on SubGroup. More general than a boolean, but it weakens "required" and still needs the same scheduler changes.
  • D. Reject at admission. The PodGroup has no pod templates, so only the PodGrouper could detect heterogeneity. Fragile.

2Promotion raises the protected quota (in-place resize and pod replacement)

Mechanism

  • The resize validator checks core pods only. Upsizing an elastic pod is allowed over-quota.
  • A core pod dies. The next-oldest allocated pod, now larger, takes the slot. Nobody asks the quota gate. Queue protected usage rises by the size difference, and the queue can sit above its deserved quota with unreclaimable pods.
  • Contrast with non-preemptible: every pod, including a replacement, passes the non-preemptible gate at allocation. Semi-preemptible elastic pods skip it, so promotion is an ungated reclassification.
  • Related: a Releasing pod is not active-allocated, so its core slot is vacated before its resources are freed.

Options

  • A. Gated promotion + pinned core. Core membership persists (from the published CorePods) and changes only by promotion. A promotion that raises the charge must pass the existing IsNonPreemptibleJobOverQuota check. If it fails, the pod stays elastic and the job reports a "core-deficit" condition. This also fixes the core flip, and it was already deferred as "pin to CorePods".
  • B. Admitted core budget. Store the per-leaf core request vector at gang-phase admission. A pod is core-eligible only if its request fits the budget. Simpler, but a rollout to a bigger spec leaves slots permanently vacant, so the job silently runs with less than minMember protected.
  • C. Accept and document. Treat it like the accepted quota scale-down. Unlike scale-down, a user action triggers it and the growth is unbounded.

2*Rollouts the scheduler does not control must not violate quota

Every rollout strategy reduces to the same event: a pod joins the core. So the invariant belongs at the classification step, not in rollout handling: the protected charge may increase only through the quota gate. Option 2A enforces this for all of the cases below.

HLD · Issue 1 — subgroup coloring (isCore)

Proposal

  • New optional field on SubGroup: isCore: true. Unset means today's behavior (satisfied first, then name).
  • Meaning: this subgroup holds one of its parent's minimal-satisfying slots. It chooses which sibling is protected. How much is protected stays the subgroup's own min shape (minMember / minSubGroup). There is no third tier.
  • Valid on leaves and sets, as a child of a node with a partial minSubGroup. Elsewhere it is a no-op.

Our take

  • Support it. It fixes the root cause (the user cannot say which subgroup matters) instead of documenting around it. Nesting stays as the zero-API guidance for interchangeable siblings.
  • Side benefit: marked slots have a fixed identity, so they cannot flip. That removes the core-flip for them.
  • The field is cheap; the semantics are not. "Min satisfied" changes from a count to count plus identity, and it is read in about six places. If one is missed, allocator, eviction and quota disagree, which is the property #1804 was built to guarantee. The design below funnels it through one place.
  • It does not fix issue 2. Leaf-level promotion and unmarked fill slots still need the gate (2A).

Semantics (per SubGroupSet with minSubGroup = m and c marked children)

RuleDefinition
Required set RThe marked children first, then m − c slots filled by today's rule (satisfied first, then name). |R| = m always, so the protected charge never exceeds m slots.
Min satisfiedEvery marked child satisfied AND at least m children satisfied. Previously a count only. This drives gang vs elastic allocation, the zero charge for elastic pods, and stale-eviction.
Gang phase collectsAll unsatisfied marked children first, then unsatisfied unmarked children up to max(0, m − c − satisfiedUnmarked). All of it is charged as core. The elastic phase runs only after min is satisfied and charges 0.
Surplus (evictable whole)Satisfied children outside R. A member of R is never evicted, at any depth. An unmarked child beyond the m slots is never promoted into R, so there is no ungated charge.

Validation rules

  • Reject when the marked children of a parent outnumber its effective minSubGroup.
  • Reject changes to isCore on a semi-preemptible PodGroup (add, remove or move). It changes the protected set without admission, the same class as the min-increase rule.
  • Warn and ignore on a group whose preemptibility is explicitly set to another mode. It cannot be rejected because preemptibility may resolve from the priority class.
  • Redundant marks (parent minSubGroup unset, so all children are required) are accepted.

Behavior to document

  • If a marked subgroup cannot be scheduled, the job does not start, even if unmarked subgroups would fit. That is intended: "required" means required.
  • An older scheduler ignores the field and falls back to the name rule. This is safe for quota but the marking is not honored.
  • Marking every child is equivalent to leaving minSubGroup unset.

Open questions for the team

  • Protect the subgroup's min shape, or everything in it? We propose the min shape. "Everything" adds a third tier (required for scheduling, protected, elastic) and breaks the invariant that core equals the minimal satisfying set.
  • Name: isCore exposes internal vocabulary. required matches minSubGroup and says what the scheduler enforces. Also, Kubernetes API style avoids an is prefix on booleans.
  • Bool or rank? An integer rank removes the marked-count rule but weakens "required". Not recommended.
  • Immutable or unmarkable? We propose immutable. Unmarking can move the slot to a larger sibling, which is a charge increase.
  • Scope of the first PR: the field plus scheduler semantics only, or Grove sourcing in the same change?

Phasing and tests

P1 API field + webhook in kai-scheduler/api → P2 scheduler semantics, repin → P3 PodGrouper plumbing (Grove first) → P4 docs and example. Tests: unit coverage on SubGroupSet, core, allocation and eviction; a property test that eviction never returns a member of R and the gang phase always covers the marked children; an integration reclaim test on the example above; one E2E spec where the name rule and isCore disagree.

Decisions to brainstorm
  1. Issue 1: adopt isCore coloring? Settle the HLD open questions, mainly whether it protects the subgroup's min shape or everything in it. It reopens the "no new API fields" goal and ships through kai-scheduler/api.
  2. Issue 2 / 2*: do we adopt "protected charge rises only through the quota gate" as the invariant? That implies pinned core membership, which means a status read-back that the HLD rejected for the alpha.
  3. Scope: fix on this branch, or split into (a) validation gaps (preemptibility flip, resize), (b) gated promotion, (c) docs and tests?
